Governed memory for AI coding agents

AI coding agents forget everything between sessions. We gave them a memory they could share, without letting one client's knowledge reach another, and measured whether they actually used it.

~12 weeksMVP design to production
~1,400automated tests across 4 repos
1 ringper session, fail-closed

The problem

Engineers at a consultancy use agents in Claude Code, Codex and other editors every day. Each session starts from zero: the agent relearns the codebase, repeats mistakes someone already fixed, and never benefits from decisions made last week. The obvious fix, a shared memory, collides with the consultancy's first obligation: knowledge from one client engagement must never reach another.

So the job was not "add memory". It was memory with isolation, auditability and evidence of value, built quickly enough to matter.

Scope before code

The program started broader than twelve weeks allowed. I led a scope reset that cut the MVP down to the memory and governance layer, wrote a roadmap with phase gates and kill criteria agreed before work began, and kept a log of more than twenty decisions with their rationale. The work split into four repositories: application, Terraform, GitOps and program.

Agreeing on kill criteria up front turned later debates into checks against the criteria, not arguments about sunk cost.

One front door

Every agent connects to a single entry-point service built with Python, FastAPI and the MCP SDK. It is the only place where identity is decided:

agent (Claude Code, Codex, ...)
   │  MCP + OAuth 2.1 token (Entra ID)
   ▼
front door ── verify token ── bind session to exactly one engagement ("ring")
   │            cannot confirm access? ──► refuse (fail closed)
   │  signed identity
   ▼
memory engine for that ring  (own encryption key, own placement)
   │
   └──► audit record for every tool call
  • A session belongs to one engagement for its whole life. Anything ambiguous is refused.
  • The front door signs the identity it passes downstream, so engines never trust the caller directly. Signing keys rotate, and the service runs as multiple replicas.
  • Every tool call writes an audit record.

Isolation at every layer

A single check is a single point of failure, so isolation is repeated at each layer:

  • Data: each engagement has its own encryption key and its own engine placement.
  • Configuration: engagements are created from a reviewed file in Git, never by hand.
  • Automation: CI pipelines get access through a GitHub OIDC machine identity bound to one engagement.
  • Verification: an automated leakage drill and per-engagement canary probes run in CI and in production, and any failure raises an alert.

Proving it is used

AI tooling is easy to launch and hard to justify. The platform links each recall to the later moment when what it returned is cited in the agent's work. A Postgres telemetry pipeline rolls that up daily and monthly, reconciles counts against the audit records, and uses retention rules that cannot delete data before it has been rolled up.

Usage baselines were frozen for each engagement before recall was switched on, so the dashboards show change against a real before, including knowledge recalled across different users.

Infrastructure

AWS from development to production: Terraform modules for the account baseline, EKS, tenants and telemetry, with separate plan and apply roles through GitHub OIDC; Flux GitOps for cluster state; images pinned by digest and promoted from dev to prod through a verified step; default-deny network policies; and an embedding model baked into its image so the cluster needs no internet access. Observability runs on the Grafana LGTM stack.

How we built it

  • The repositories used their own product: agents recalled from and wrote to the platform while building it.
  • Every pull request got a red-team pass that required running the code to prove its claims, and CI checked that the evidence was there.
  • Developers connect with one command and single sign-on; operators create, check and offboard engagements by opening reviewed pull requests, with quota preflight checks and rollback.

What I would keep

  • Decide identity in exactly one place and make everything downstream verify it.
  • Treat "can't confirm" as "no".
  • Freeze the baseline before launch, or adoption numbers mean nothing.
  • Kill criteria are cheapest to agree on before anyone has written code.
